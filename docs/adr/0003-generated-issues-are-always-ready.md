# 0003: Generated Issues are always ready

- **Status:** Accepted
- **Date:** 2026-11-20
- **Supersedes:** [0002](0002-visual-checks-are-human-in-the-loop.md)

## Context

ADR 0002 made a `ready` Issue promise that every acceptance check is executable.
An Issue with any visual or manual check was moved to `needs-human`, both by the
`to-issues` skill and by a `report_issues` safety net.

That rule hid work the Developer wanted an Agent to start. The `todo-app` Plan
produced an Issue, "Apply the Material 3 Google-style theme", with two visual
checks and one executable check (`bun run check`). It was published as
`needs-human`, so it waited for the Developer even though an Agent could do the
implementation and the automated check. The label also surprised the Developer:
the Plan review screen does not explain why a slice it just generated is not
ready.

The rule also duplicated a decision the Developer can make by reading the Issue
and moving it by hand.

## Decision

Every Issue generated by a Grill-Me Session is labelled `ready`, whatever its
acceptance checks look like. YAAABK never relabels a generated Issue.

- The `to-issues` skill labels every slice `["ready"]`.
- `normaliseGeneratedIssues` stores the labels the agent reported. There is no
  acceptance-check review and no automatic relabel.
- `needs-human` stays in the Issue label set for runtime escalation only: an
  Agent that runs out of budget or attempts, or CI that cannot resolve a branch,
  moves the Issue there. A generated Plan never uses it.

The `to-issues` skill still prefers executable acceptance checks, because they
let the Agent verify its own work, and it still forbids browser-installation
checks the text-only Agent cannot satisfy. If a slice needs a Developer's eye,
the body says what to look at and the Developer checks the pull request.

## Consequences

- Visual and mixed slices reach the ready queue and an Agent may attempt them.
  The Developer reviews the visual result in the pull request.
- The readiness policy and its shared module (`acceptance-check.ts`) are
  removed, along with the `relabelled` field on the reporting result.
- ADR 0002 is superseded. Its concern about a text-only model and a browserless
  Agent image still applies to the wording of acceptance checks, not to labels.
- A generated Issue with a genuine human-only decision is no longer labelled
  `needs-human` at creation. The Developer can move it after reading it.
